Behind this slide: a real test day () replayed at speed. Every dot is a loop detector, every line a road connection. Red is slow. Watch the evening rush spread along the lines: that spreading is what this project tries to exploit.

Traffic is contagious

A crash on the 101 does not stay on the 101. The queue grows backwards, sensor by sensor, at walking pace.

So a sensor's future speed depends on its own past and on what is already happening upstream and downstream.

Task: from the last 60 minutes at every sensor, predict speed 5, 15, 30 and 60 minutes ahead.

Frame the question. Independent models only see the left half of that sentence.

The data has holes

of all readings are missing (stored as 0 mph)

five-minute steps where every sensor is down at once

A zero is a broken sensor, not a standstill. Models get a mask: missing inputs are flagged, missing targets carry no loss and are never scored.

Hollow grey rings on the map are sensors reporting nothing at that moment. Zero-filling would teach the model fake jams. The test period is worse: of test targets are missing.

Phase 1 set the bar

XGBoost on lags, rolling statistics and calendar features beat persistence by at 60 minutes.

Giving it its neighbours' speeds as extra columns helped again: the graph carries signal.

But a tree only sees fixed, hand-made neighbour summaries. It cannot learn how a jam travels.

Recap only. Numbers come from the same test points used today.

The road is a graph, and it has direction

Edges come from real road distances, not straight lines: directed connections.

Only of them run both ways. Upstream feeds a sensor; downstream is where its queue will go.

Highlighted: the best-connected sensor and its neighbours.

Graph built with DCRNN's thresholded Gaussian kernel on road distance. We never symmetrise it, and we never load the pickle that ships with DCRNN (pickles can run code).

One idea per step

1

GRU, time only

One recurrent network shared by all sensors. Sensors never see each other.

1b

ST-GAT with every edge removed

Identical network and parameter count to step 2. The control group.

2

ST-GAT: GRU + graph attention

Each sensor reads its neighbours and learns how much each one matters, right now.

3

DCRNN: diffusion inside the GRU

Information spreads like a random walk along roads, at every step of an encoder-decoder.

Every rung changes one thing, so every gain has one cause. Step 1b is the experiment that matters: same model, graph switched off.

Attention: who should I listen to?

After the GRU summarises each sensor's last hour, every sensor sends that summary to its neighbours.

A small learned scorer weighs each incoming message. Weights are softmaxed per sensor, so they sum to one, and recomputed for every moment.

Separate attention for upstream and downstream edges; two layers reach neighbours of neighbours.

GATConv from PyTorch Geometric. Pulses on the map: messages moving to one sensor, thickness = attention weight from the trained model on the test period.

Training, fairly

  • Same 83 / 12 / 24 day split as Phase 1, cut at midnight
  • Predict the change from the last observed speed; masked MAE loss
  • Early stopping and checkpoint choice on validation only
  • Learning rate and width searched on validation for both ST-GAT and its no-edge twin
  • Trained on a Kaggle Tesla T4; test data touched once, at the end

Against the literature

Paper protocol: all horizons, zeros masked, their own 70/10/20 split by sample. Ours differs slightly (day-aligned split, predictions clipped to 0–70 mph), so this is a sanity check, not a leaderboard.

Published numbers from the DCRNN (Li et al., ICLR 2018) and Graph WaveNet (Wu et al., IJCAI 2019) papers.

What we do not claim

  • One city, 119 days in 2012, speed only. No claim beyond that.
  • Attention weights are a description of the model, not proof of cause.
  • DCRNN here is our re-implementation, not the authors' code.
  • Nothing controls real traffic. Signal control in this project is simulated only.
Say these before someone asks.
