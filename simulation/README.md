# Simulated signal-control experiment (optional)

> **Status: executed** with SUMO 1.28 (`pip install eclipse-sumo traci`) in notebook 09: 20 seeds x 2 policies, paired comparison; results in
> `artifacts/metrics/sumo_signal_control_*.csv` and summarised in `reports/results_summary.md`. Every simulation step checks that SUMO displays the controller's signal state.
> This is a *simulation only*: the project never connects to real traffic signals, detectors or live feeds.

## Why METR-LA cannot drive this directly

METR-LA gives speeds at 207 highway sensors. It has no intersection geometry, signal plans, turning movements, queues or vehicle counts,
so its sensor graph is **not** a signal-control network. This experiment therefore uses a small, self-contained synthetic intersection
and only illustrates the *idea* that a forecast of demand/congestion could inform a signal policy (hook: `QueueAwarePolicy.forecast`).

## Contents

| File | Purpose |
|---|---|
| `signal_policies.py` | `FixedTimePolicy`, `QueueAwarePolicy` and a `SignalController` state machine that enforces min/max green, yellow, all-red and never shows conflicting greens (tested in `tests/test_signal_policies.py`) |
| `run_sumo_experiment.py` | writes the network (`sumo_config/*.xml`), generates seeded Poisson demand, runs TraCI episodes and checks the displayed signal state every step |
| `sumo_config/` | node / edge / connection files of the 4-way intersection (generated by the notebook) |

## Scenario

* 4-way intersection, one lane per approach, 250 m arms, 50 km/h, straight-through movements only (so phases cannot conflict inside a phase).
* Two-phase signal: north-south / east-west.
* Demand 3,600 s, seeded Poisson arrivals: first half 500 veh/h per N/S approach and 200 veh/h per E/W approach; second half reversed.
* Policies: fixed-time 30 s / 30 s versus queue-aware (min green 10 s, max green 60 s, yellow 3 s, all-red 2 s for both).
* Metrics: mean waiting time, mean travel time, mean and maximum queue (halting vehicles on the incoming lanes), completed trips; 20 seeds, paired by seed.
* Caveat: the fixed-time plan (30 s / 30 s) is not tuned to the asymmetric demand, so the measured improvement is an upper bound for this scenario.

## Requirements

SUMO >= 1.18 with TraCI. Example install (no admin rights needed):

```bash
pip install eclipse-sumo traci          # provides `sumo`, `netconvert`; then:
export SUMO_HOME="$(python -c 'import sumo; print(sumo.SUMO_HOME)')"
```

or install SUMO from <https://sumo.dlr.de/docs/Installing/index.html>. Then run notebook `09_optional_sumo_simulation.ipynb`.

## Implementation plan if you extend this

1. Tune the fixed-time plan to the demand (e.g. Webster's method per half hour) for a fairer baseline.
2. Vary the demand level towards and beyond capacity to see where the policies differ in throughput.
3. Optionally feed a demand forecast into `QueueAwarePolicy.forecast` (e.g. expected arrivals per approach from a short-term predictor).
4. For a realistic study, import a real intersection (OpenStreetMap + `netconvert`) and calibrate demand from counts.
